# Requirements Document

## Introduction

The Agentic Math Learning System is a monorepo demo application designed to teach students how to build Agentic RAG (Retrieval-Augmented Generation) systems and stateful agentic workflows. The system exposes three distinct agentic paths — an Adaptive Tutor, a Practice Agent, and a Doc-to-Concept Agent — each demonstrating a different combination of LangGraph orchestration, ChromaDB vector search, LlamaParse PDF extraction, and a local Ollama LLM. The codebase is intentionally "simple by design" so that every architectural decision (prompt structure, tool definition, embedding pipeline, reranking) is visible and educational.

The backend is built with FastAPI (Python) and the frontend with React + Tailwind CSS, deployed together via Docker Compose.

---

## Glossary

- **System**: The Agentic Math Learning System as a whole.
- **Backend**: The FastAPI Python application that hosts all agentic logic.
- **Frontend**: The React + Tailwind CSS single-page application.
- **LangGraph_Orchestrator**: The LangGraph state-machine engine that manages agentic workflow execution.
- **Ollama_LLM**: The locally running Ollama instance serving the `llama3:latest` model.
- **LlamaParse_Pipeline**: The LlamaIndex LlamaParse component responsible for PDF-to-Markdown extraction.
- **ChromaDB**: The vector database used to store and retrieve embedded document chunks.
- **PostgreSQL**: The relational database used to persist session state and student progress.
- **Reranker**: The local cross-encoder model (`BAAI/bge-reranker-v2-m3`) used to rerank retrieved chunks.
- **Router**: The LangGraph node that classifies an incoming query and routes it to the appropriate tool or retrieval path.
- **Adaptive_Tutor**: Path A — the RAG-based chat agent that answers math questions using retrieved context and CoT prompting.
- **Practice_Agent**: Path B — the stateful MCQ generation and feedback agent.
- **Doc_to_Concept_Agent**: Path C — the PDF ingestion and concept-extraction agent.
- **MCQ**: Multiple-choice question generated by the Practice_Agent.
- **Deep_Dive_Tool**: A LangGraph tool node invoked when a student answers an MCQ incorrectly, providing a detailed concept explanation.
- **Chunk**: A semantically segmented piece of text produced by the chunking strategy applied to parsed Markdown.
- **Embedding**: A numerical vector representation of a Chunk stored in ChromaDB.
- **CoT**: Chain-of-Thought — a prompting technique that instructs the LLM to reason step-by-step before producing a final answer.
- **Session**: A PostgreSQL-persisted record of a student's interaction with one of the three agentic paths.

## Requirements

### Requirement 1: Monorepo Project Structure

**User Story:** As a student, I want to explore a clearly organized monorepo, so that I can understand how the backend and frontend are separated and how they relate to each other.

#### Acceptance Criteria

1. THE System SHALL provide a monorepo root containing at minimum a `/backend` directory, a `/frontend` directory, a `docker-compose.yml` file, and a `.env.example` file.
2. THE Backend SHALL be organized with clearly named modules for each agentic path (`adaptive_tutor`, `practice_agent`, `doc_to_concept`), shared utilities (`embeddings`, `reranker`, `database`), and LangGraph graph definitions.
3. THE Frontend SHALL be organized with clearly named components corresponding to each of the three agentic paths.
4. THE System SHALL include inline code comments at every architectural boundary explaining the purpose of each module, class, and non-trivial function.

---

### Requirement 2: Infrastructure and Deployment

**User Story:** As a student, I want to spin up the entire system with a single command, so that I can focus on learning the agentic patterns rather than configuring infrastructure.

#### Acceptance Criteria

1. THE System SHALL provide a `docker-compose.yml` that defines services for the FastAPI Backend, PostgreSQL, and ChromaDB.
2. THE System SHALL provide a `.env.example` file that documents every required environment variable, including `LLAMA_PARSE_API_KEY`, `OLLAMA_BASE_URL`, `POSTGRES_DSN`, and `CHROMA_HOST`.
3. WHEN a student runs `docker-compose up`, THE System SHALL start all services and make the Backend API reachable on a documented port within the compose network.
4. THE Backend SHALL read all secrets and configuration exclusively from environment variables; no secrets SHALL be hardcoded in source files.

---

### Requirement 3: LLM Configuration Transparency

**User Story:** As a student, I want to see exactly how LLM parameters are set for different tasks, so that I can understand the effect of temperature and token limits on AI output quality.

#### Acceptance Criteria

1. THE Backend SHALL define a shared `LLMConfig` dataclass or equivalent structure that holds `model`, `temperature`, and `max_tokens` for each task type.
2. THE Backend SHALL use a lower `temperature` value (≤ 0.2) for math-solving and formula-extraction tasks and a higher `temperature` value (≥ 0.7) for synthetic example generation tasks, with each value accompanied by an inline comment explaining the rationale.
3. THE Ollama_LLM SHALL be invoked exclusively through a single wrapper function or class so that all call sites are consistent and the configuration is visible in one place.
4. WHEN the Ollama_LLM is invoked, THE Backend SHALL log the task name, model name, temperature, and max_tokens at DEBUG level so students can observe the parameters at runtime.

---

### Requirement 4: Vector Embedding Pipeline

**User Story:** As a student, I want to see the complete flow from raw text to searchable vector, so that I can understand how RAG systems store and retrieve knowledge.

#### Acceptance Criteria

1. THE Backend SHALL implement an embedding pipeline with clearly separated, sequentially named steps: `parse → chunk → embed → store`.
2. WHEN a document is ingested, THE Backend SHALL log each pipeline step name and the count of chunks produced or stored at INFO level.
3. THE Backend SHALL use a single, documented embedding model for all vectorization, with the model name defined as a named constant.
4. THE ChromaDB SHALL store each Chunk with metadata fields including `source_document`, `chunk_index`, `topic`, and `chunk_type` (e.g., `"formula"`, `"explanation"`, `"example"`).
5. WHEN a semantic search is performed, THE Backend SHALL retrieve the top-K candidates from ChromaDB (K defined as a named constant, default 10) before passing them to the Reranker.

---

### Requirement 5: Reranker Integration

**User Story:** As a student, I want to see how a cross-encoder reranker improves retrieval quality over raw vector similarity, so that I can understand the two-stage retrieval pattern.

#### Acceptance Criteria

1. THE Reranker SHALL be implemented as an isolated Python module with a single public function that accepts a query string and a list of candidate chunks and returns a reranked list.
2. THE Reranker SHALL use the `BAAI/bge-reranker-v2-m3` model loaded via `sentence-transformers`, with the model name defined as a named constant.
3. THE Backend SHALL return only the top-N reranked chunks to the LLM context (N defined as a named constant, default 3), with an inline comment explaining why fewer chunks reduce hallucination risk.
4. WHEN reranking is performed, THE Backend SHALL log the original retrieval order and the reranked order at DEBUG level so students can observe the improvement.

---

### Requirement 6: Path A — Adaptive Tutor (RAG Chat)

**User Story:** As a student, I want to interact with an adaptive math tutor that retrieves relevant knowledge and reasons step-by-step, so that I can see how RAG and CoT prompting work together.

#### Acceptance Criteria

1. THE Adaptive_Tutor SHALL expose a POST endpoint `/api/tutor/chat` that accepts a `session_id`, `query`, and optional `topic` field.
2. WHEN a chat request is received, THE Router SHALL classify the query as either `"knowledge_required"` or `"direct_answer"` before any retrieval is performed, with the classification decision logged at INFO level.
3. WHEN the Router classifies a query as `"knowledge_required"`, THE Adaptive_Tutor SHALL execute the full `retrieve → rerank → generate` pipeline.
4. WHEN the Router classifies a query as `"direct_answer"`, THE Adaptive_Tutor SHALL invoke the Ollama_LLM directly without retrieval.
5. THE Adaptive_Tutor SHALL construct all prompts using clearly delimited XML tags (e.g., `<context>`, `<question>`, `<instructions>`) so that the prompt structure is visible in the source code.
6. THE Adaptive_Tutor SHALL include a CoT instruction block in every math-solving prompt that instructs the Ollama_LLM to list reasoning steps before stating the final answer.
7. THE Adaptive_Tutor SHALL persist each turn (query, retrieved chunks, LLM response) to a PostgreSQL `tutor_sessions` table identified by `session_id`.
8. WHEN a session does not exist, THE Adaptive_Tutor SHALL create a new session record in PostgreSQL before processing the first turn.

---

### Requirement 7: Path B — Practice Agent (Stateful MCQ Interaction)

**User Story:** As a student, I want to practice math topics through adaptive MCQs that explain mistakes, so that I can see how a stateful LangGraph agent manages multi-turn interaction.

#### Acceptance Criteria

1. THE Practice_Agent SHALL expose a POST endpoint `/api/practice/start` that accepts a `topic` and `difficulty_level` and returns a generated MCQ with four answer options.
2. THE Practice_Agent SHALL expose a POST endpoint `/api/practice/answer` that accepts a `session_id`, `question_id`, and `selected_option`.
3. WHEN a student submits a correct answer, THE Practice_Agent SHALL return a success response and advance the LangGraph state to `"next_question"`.
4. WHEN a student submits an incorrect answer, THE Practice_Agent SHALL invoke the Deep_Dive_Tool and return a detailed concept explanation before setting the LangGraph state to `"retry"`.
5. THE Deep_Dive_Tool SHALL be defined as an explicit Python function decorated or registered as a LangGraph tool, with a docstring explaining its purpose for educational clarity.
6. THE Practice_Agent SHALL generate MCQs using the Ollama_LLM with `temperature ≤ 0.2` to ensure deterministic, well-formed questions.
7. THE Practice_Agent SHALL persist the full state machine history (question, student answer, outcome, explanation if triggered) to a PostgreSQL `practice_sessions` table.
8. THE LangGraph state schema for the Practice_Agent SHALL be defined as a typed Python dataclass or TypedDict and included in the source with comments explaining each field.

---

### Requirement 8: Path C — Doc-to-Concept Agent (LlamaParse Pipeline)

**User Story:** As a student, I want to upload a math PDF and have the system extract formulas and generate examples, so that I can see how document parsing, semantic chunking, and agentic analysis work end-to-end.

#### Acceptance Criteria

1. THE Doc_to_Concept_Agent SHALL expose a POST endpoint `/api/docs/upload` that accepts a PDF file upload and an optional `topic` label.
2. WHEN a PDF is received, THE LlamaParse_Pipeline SHALL extract the document content to Markdown using LlamaParse with math-optimized settings, preserving LaTeX or Unicode representations of equations.
3. WHEN LlamaParse extraction is complete, THE Doc_to_Concept_Agent SHALL apply semantic chunking to the resulting Markdown, producing Chunks with a target size defined as a named constant (default 512 tokens).
4. WHEN chunking is complete, THE Doc_to_Concept_Agent SHALL classify each Chunk as `"formula"`, `"explanation"`, or `"example"` using the Ollama_LLM and store the classification in the Chunk metadata.
5. WHEN all Chunks are classified, THE Doc_to_Concept_Agent SHALL embed and store each Chunk in ChromaDB with its full metadata.
6. THE Doc_to_Concept_Agent SHALL invoke the Ollama_LLM to extract all distinct math formulas from `"formula"`-classified Chunks and return them as a structured list.
7. FOR EACH extracted formula, THE Doc_to_Concept_Agent SHALL generate at least two synthetic worked examples using the Ollama_LLM with `temperature ≥ 0.7` to encourage variety.
8. THE Doc_to_Concept_Agent SHALL expose a GET endpoint `/api/docs/{document_id}/concepts` that returns the extracted formulas and their synthetic examples.
9. WHEN LlamaParse returns an error or the uploaded file is not a valid PDF, THE Doc_to_Concept_Agent SHALL return an HTTP 422 response with a descriptive error message.

---

### Requirement 9: Prompt Engineering Transparency

**User Story:** As a student, I want to read prompts that are clearly structured and commented, so that I can learn best practices for prompt engineering.

#### Acceptance Criteria

1. THE Backend SHALL define all prompts as named string constants or template functions in a dedicated `prompts.py` module, not inline within business logic.
2. THE Backend SHALL use XML-style delimiters (`<context>`, `<question>`, `<instructions>`, `<examples>`, `<output_format>`) consistently across all prompts.
3. EACH prompt constant or template SHALL include a Python docstring or inline comment that explains the purpose of each delimiter section.
4. THE Backend SHALL include at least one In-Context Learning example within the Adaptive_Tutor prompt to demonstrate few-shot prompting technique.

---

### Requirement 10: Tool Definition Transparency

**User Story:** As a student, I want to see how Python functions are registered as LangGraph tools, so that I can understand how an LLM decides to call external capabilities.

#### Acceptance Criteria

1. THE Backend SHALL define all LangGraph tools as standalone Python functions in a dedicated `tools.py` module per agentic path.
2. EACH tool function SHALL have a complete docstring describing its purpose, input parameters, and return value, because LangGraph uses the docstring to inform the LLM about the tool's capability.
3. THE Backend SHALL include an inline comment at each tool registration site explaining how LangGraph exposes the tool to the Ollama_LLM.
4. THE LangGraph_Orchestrator SHALL define the graph topology (nodes, edges, conditional edges) in a single, clearly commented function per agentic path so students can trace the full execution flow.

---

### Requirement 11: Frontend Interface

**User Story:** As a student, I want a simple web interface to interact with all three agentic paths, so that I can observe the system behavior without writing API calls manually.

#### Acceptance Criteria

1. THE Frontend SHALL provide three clearly labeled navigation tabs or sections corresponding to Path A (Adaptive Tutor), Path B (Practice Agent), and Path C (Doc-to-Concept Agent).
2. THE Frontend SHALL display the full LLM response including any CoT reasoning steps in a readable, formatted view.
3. WHEN the Practice_Agent returns a Deep_Dive_Tool explanation, THE Frontend SHALL visually distinguish the explanation from the standard MCQ feedback (e.g., different background color or icon).
4. THE Frontend SHALL display a loading indicator WHILE any Backend API call is in progress.
5. THE Frontend SHALL display a descriptive error message WHEN a Backend API call returns a non-2xx HTTP status.
6. THE Frontend SHALL allow a student to upload a PDF file for Path C and display the extracted formulas and synthetic examples upon completion.

---

### Requirement 12: Parser and Serializer Round-Trip Integrity

**User Story:** As a student, I want the system to reliably serialize and deserialize data between components, so that I can trust that no information is lost as data flows through the pipeline.

#### Acceptance Criteria

1. THE Backend SHALL define Pydantic models for all API request and response bodies, ensuring that serialization and deserialization are handled by a single, consistent mechanism.
2. FOR ALL valid API request objects, serializing to JSON and then deserializing back SHALL produce an equivalent object (round-trip property).
3. WHEN a Pydantic model validation error occurs on an incoming request, THE Backend SHALL return an HTTP 422 response with field-level error details.
4. THE LlamaParse_Pipeline SHALL preserve all LaTeX math expressions through the parse → Markdown → chunk pipeline without loss or corruption of equation syntax.
